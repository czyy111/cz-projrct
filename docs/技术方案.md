## 技术目标

- 第一版交付中文 iOS 应用，Android 后续支持。
- 无账号、无业务服务器也能使用手工计划和全部本地任务功能。
- 目标、任务、草稿和记录可靠保存在本地。
- API Key 与普通业务数据分离保存。
- 使用 iOS 系统本地通知。
- 支持多套用户自定义大模型配置。
- AI 输出经过结构校验和用户确认后才写入正式计划。
- 后续可以扩展 Android，但不为跨平台而牺牲第一版数据可靠性和通知稳定性。

## 当前环境约束

当前工作区运行在 Windows。

- Apple 的 iOS 本地构建、模拟器和完整真机调试依赖 Xcode，而 Xcode 运行在 macOS。
- Flutter 官方 iOS 设置同样要求 Xcode；使用原生 iOS 插件时通常还需要 CocoaPods。
- React Native 本地 iOS 开发同样依赖 Xcode。
- Expo EAS Build 可以从 Windows 提交项目，在 Expo 的 macOS 云环境生成 iOS 构建；但这引入 Expo 账号、云端构建和服务依赖。
- 无论使用哪种框架，发布 App Store 都需要 Apple Developer 相关账号和签名能力。

用户已确认接受 Expo 云构建。因此，第一版可以在 Windows 上进行主要开发，并通过 EAS 的 macOS 云环境生成 iOS 构建；没有 Mac 所带来的真机调试限制仍需纳入测试安排。

## 客户端框架候选

### 方案 A：原生 SwiftUI

建议组合方向：Swift、SwiftUI、Apple 原生数据与系统框架。

优点：

- Apple 将 SwiftUI定位为创建新应用的优先选择之一。
- 与本地通知、Keychain、系统主题、减少动态效果和 iOS 生命周期直接集成。
- 第一版只有 iOS 时，系统行为最可控。
- 可以减少跨平台桥接和插件依赖。
- 适合本产品重视本地数据、通知和系统体验的特点。

缺点：

- Android 后续需要单独开发 Kotlin/Compose 客户端，或未来重写共享层。
- 必须使用 macOS 和 Xcode 开发、调试与构建。
- 团队需要 Swift/iOS 能力。

实现难度：iOS MVP 中等；后续双平台总体难度高。

适用条件：iOS 体验和稳定性优先，并且可以使用 Mac。

### 方案 B：Flutter

建议组合方向：Dart、Flutter，加必要的 iOS/Android 原生插件。

优点：

- iOS 和 Android 可以共享大部分界面和业务逻辑。
- 自定义视觉、深色模式和动画实现一致。
- Android 后续开发成本通常低于重新编写原生客户端。
- 目标、任务、AI 解析等纯业务逻辑适合共享。

缺点：

- iOS 本地构建和调试仍需要 macOS、Xcode；原生插件可能需要 CocoaPods。
- Keychain、本地通知、通知快捷操作和系统设置跳转通常依赖插件或原生桥接。
- 需要持续验证插件与最新 iOS/Android 系统的兼容性。
- 界面需要额外注意 iOS 原生交互习惯。

实现难度：MVP 中等；后续双平台中等。

适用条件：确定会开发 Android，并且可以接受跨平台插件管理。

### 方案 C：React Native＋Expo

建议组合方向：TypeScript、React Native，使用 Expo 框架和必要原生模块。

优点：

- React Native 官方建议新项目使用框架，Expo 是其列出的生产级框架选择。
- iOS 和 Android 可以共享大部分代码。
- Expo EAS Build 可以在云端生成 iOS 构建，Windows 环境也能发起构建和提交。
- TypeScript 生态成熟，网络请求和 JSON 处理直接。

缺点：

- 使用 EAS 云构建会引入 Expo 账号、云端构建和可能的服务限制。
- 深度原生能力可能需要原生模块；React Native 官方资料也说明部分 Swift 模块仍涉及 Objective-C++ 桥接。
- 需要严格筛选支持新架构的通知、本地数据库和安全存储方案。
- 如果不使用云构建，本地 iOS 调试仍需要 Mac/Xcode。

实现难度：使用 Expo 时 MVP 中等；复杂原生扩展中高。

适用条件：希望跨平台，并且当前没有 Mac但能接受 Expo 云构建。

## 已确认的客户端技术路线

- 客户端框架：React Native＋Expo。
- 开发语言方向：TypeScript。
- iOS 构建方式：Expo EAS 云构建。
- 当前开发设备：Windows 电脑。
- 第一版真机测试设备：iPhone 16 Pro Max。
- 用户当前 iPhone 系统版本：iOS 26.6。
- 第一版交付方式：仅供用户本人在自己的 iPhone 使用，暂不上架 App Store。
- 后续 Android 版原则上复用可共享的界面和业务代码，具体适配在 Android 阶段另行确认。

该选择只解决客户端框架和 iOS 构建路径，不代表已开始开发，也不改变“数据优先保存在手机本地、暂不提供云同步”的产品决定。EAS 云端仅用于编译安装包，不用于保存用户的目标、任务和计划数据。

### 已知限制

- 需要注册 Expo 账号才能使用 EAS 云构建。
- 构建时项目源文件会上传至 Expo 的构建环境。
- 在真实 iPhone 上安装签名构建以及发布 App Store，需要符合 Apple 的开发者账号与签名要求。
- Windows 无法运行 iOS 模拟器；通知、后台行为、安全存储和系统权限必须重点安排真实 iPhone 测试。
- 遇到深层 iOS 原生问题时，没有 Mac/Xcode 会降低排查效率，必要时可能需要临时使用云端或其他 Mac 环境。

### 仅本人使用时的安装说明

- 暂不上架 App Store，不需要设计商店页面或执行公开发布流程。
- Expo Go 可以在前期免费预览主要界面和部分本地功能，但它是通用开发容器，不是独立的“橙橙计划”应用；应用名称、图标、原生能力和长期使用方式均有限制。
- 按 Expo 当前官方说明，在 iPhone 上安装不依赖付费 Apple Developer Program 的自定义开发构建，需要通过本地 Xcode 构建；该方式要求 Mac。
- Apple 免费 Personal Team 的签名配置通常七天到期，需要重新构建和安装；而用户当前没有 Mac，因此不适合作为稳定的长期使用方案。
- 如果希望在当前“Windows＋EAS”条件下安装独立版本并长期稳定使用，仍需要 Apple Developer Program，但不必把应用提交到 App Store。

### 已确认的分阶段安装策略

1. 技术设计完成后，开发初期先使用免费的 Expo Go 在用户 iPhone 上预览和验证兼容功能。
2. 当前不注册 Apple Developer Program，也不进行 App Store 上架准备。
3. 应用基本完成、需要独立名称与图标、完整原生能力和长期安装时，再由用户决定是否注册 Apple Developer Program。
4. 若 Expo Go 无法验证某项关键原生能力，应明确标记为“等待独立开发构建验证”，不得把未验证功能当作已完成。

## 本地数据方案（已确认）

### 主数据存储

- 使用 `expo-sqlite` 提供的 SQLite 作为业务主数据库。
- 保存目标、阶段、计划草稿、任务、任务依赖、打卡记录、操作记录、提醒设置和基础偏好。
- 采用明确的数据版本号和逐版本迁移，不允许因为版本升级或迁移失败直接清空数据库。
- 目标、任务及其关联记录需要通过事务一起更新，避免只写入部分数据。
- 数据库启用适合可靠写入的日志模式，具体参数在开发计划中通过测试确定。

### 保存时机

- 打卡、取消完成、延后、跳过、删除、恢复、重新安排、目标状态变化和计划确认等关键操作立即保存。
- AI 请求发出前先保存用户输入；AI 返回后先保存有效草稿，再进入审核页。
- 长文字编辑在用户停止输入约 1～2 秒后自动保存，并在离开页面或应用转入后台时再次保存。
- 界面只有在数据库写入成功后才显示“已保存”；失败时保留当前输入并提示重试。

### 本机恢复副本

- 在设备本地文档目录保留最近三份轮换恢复副本。
- 恢复副本包含主要业务数据和数据版本，不包含 API Key。
- 关键批次写入成功后更新恢复副本；写副本时先生成临时文件并校验，再替换轮换文件，避免中途退出破坏上一份有效副本。
- 启动时若主数据库无法正常读取，按新到旧检查恢复副本，并在恢复成功后明确告知用户。
- 本机副本只能防范部分文件损坏和异常退出，不能防范卸载应用、设备损坏或恢复出厂设置；第一版不承诺跨设备恢复。

### 数据一致性

- 通知安排失败不得删除或回滚已经保存的任务；应记录待重新安排状态，并在下次启动或权限恢复后重试。
- 逾期由当前时间和任务状态动态计算，不重复保存容易失真的“逾期状态”。
- 数据库迁移、恢复和通知重建必须有自动化测试与真实 iPhone 验证。

## API Key 安全方案（已确认）

- 使用 `expo-secure-store`，由 iOS 安全存储机制保存 API Key。
- API Key 不写入 SQLite、业务恢复副本、错误报告、分析数据或普通日志。
- 每套大模型配置只在业务数据库保存一个密钥引用标识，不保存密钥正文。
- 读取 API Key 时不要求每次进行 Face ID 验证，兼顾个人设备上的安全性、调用便利性和 Expo Go 阶段的可验证性。
- API Key 在界面中默认遮挡；仅在用户主动操作时临时显示，离开页面后重新遮挡。
- 删除一套大模型配置时，同时删除 SecureStore 中对应的密钥。
- “测试连接”只使用当前表单中的配置发起最小请求，不自动保存配置、不自动设为默认，也不得记录完整请求头。
- 应用不得假设 SecureStore 一定随卸载被清除；用户执行“清除全部数据”时必须主动删除所有已知密钥项。
- 第一版不把 API Key 加入本机恢复副本；恢复业务数据后，缺失密钥的配置应显示“需要重新填写”。

## 本地通知方案（已确认）

### 基本实现

- 使用 `expo-notifications` 调用 iOS 本地通知，不建设远程推送服务器。
- 通知由手机系统按日期和时间调度；应用不在前台时仍由系统负责尝试展示。
- 仅对“提醒已开启、目标处于执行状态、任务待完成且提醒时间有效”的任务安排通知。
- 每个有效提醒节点最多对应一个待发送系统通知。
- 系统通知标识与任务、提醒版本及安排时间一同记录在 SQLite 中。

### 滚动安排与系统限制

- 考虑 iOS 待发送本地通知数量限制，应用最多维持约 60 条时间最近的待发送通知，预留少量系统操作空间。
- 超出滚动窗口的任务仍完整保存在数据库中，但暂不提交给系统通知中心。
- 每次应用启动、任务批量变化、计划确认、权限恢复或时区与系统时间变化后，重新计算最近通知窗口。
- 如果用户长期不打开应用且未来任务超过系统窗口，较远任务可能尚未进入系统安排；设置页应如实说明这一边界。

### 任务与通知一致性

- 任务完成、跳过、删除或目标暂停后，取消尚未触发的旧通知。
- 修改提醒时间或延后任务时，取消旧通知，再按新时间安排新通知。
- 数据保存优先于通知操作；通知失败不得回滚或删除任务，而是记录“待修复”并在下次核对时重试。
- 启动时读取系统待发送通知，与数据库期望状态比对，补齐缺失项并取消已经失效的项目。
- 系统拒绝权限时保留任务和提醒设置，并提供跳转系统设置的入口。

### 通知交互与验证边界

- 目标交互为“完成”和“延后”两个快捷操作；点击通知正文进入相应任务详情。
- 快捷操作不可用或处理失败时，点击正文进入任务详情是完整备用路径。
- Expo Go 阶段验证基础本地通知、权限和时间调度。
- 快捷操作、独立应用被系统结束后的响应、关机重启和长期滚动安排，必须留到独立开发构建中进行真实 iPhone 验收。
- iOS 会尽力及时发送通知，但专注模式、系统权限等因素可能影响用户看到提醒的时间，产品不承诺绝对准时。

## 大模型接口方案（已确认）

### 双接口适配

第一版内置两类请求适配器：

1. OpenAI 兼容 Chat Completions：作为默认和主要兼容方式，用于 DeepSeek、豆包及其他提供兼容接口的国产模型服务。
2. Responses API：用于 OpenAI，以及明确提供兼容 Responses API 的服务商；火山方舟当前官方资料也提供该接口模式。

每套模型配置保存以下业务字段：

- 配置名称。
- 服务商或“通用兼容接口”。
- 接口类型。
- Base URL。
- 模型名称或模型/接入点 ID。
- API Key 的 SecureStore 引用。
- 是否为默认配置。
- 最近一次连接测试时间与结果，不保存测试请求正文和完整错误原文。

### 国产模型兼容目标

- 第一版明确把 DeepSeek 官方 API 和火山方舟豆包 API 纳入连接测试与验收范围。
- 同时提供通义千问/阿里云百炼、智谱 GLM 和“通用 OpenAI 兼容接口”的配置入口；具体可用性取决于用户账号权限、区域地址、模型名称和厂商当时的接口实现。
- 预设只帮助填写接口类型和官方地址提示，不在应用内固化可能频繁变化的模型名称、价格或可用额度。
- 不支持只有网页聊天、没有正式 API 的服务；不通过抓取网页、共享账号或非官方中转方式接入。
- 需要特殊鉴权算法、特殊签名或完全自定义请求结构的服务商不纳入第一版，除非它同时提供上述兼容接口。

### 请求与输出处理

- 手机直接向用户选择的模型服务商发送请求，橙橙计划不建设中转服务器。
- 仅发送完成本次目标追问或计划生成所需的数据，不发送无关目标、完整数据库或 API Key 正文。
- Responses API 在服务商支持时设置为不主动保存响应；服务商自身的数据处理仍受其服务条款约束。
- 优先使用服务商支持的结构化输出；若只支持 JSON Object，则使用 JSON 模式并配合明确提示词；再不支持时降级为普通 JSON 文本。
- 所有模型结果必须在本地经过 JSON 解析、字段类型、日期范围、任务关系、必填内容和数量限制校验。
- 校验失败的结果只能作为错误或可恢复草稿处理，不得直接生成正式任务或安排通知。
- 不保证所有自称兼容 OpenAI 的第三方地址都可用，以应用内“测试连接”和实际计划生成校验为准。

### 连接测试

- “测试连接”发送最小请求，分别识别地址不可达、认证失败、模型不存在、额度/限流、超时、响应格式错误和协议不兼容。
- 测试成功不自动保存配置，也不自动设为默认配置。
- 错误信息不得包含完整 API Key、Authorization 请求头或用户计划正文。
- DeepSeek 与豆包需要分别进行最小连接测试和结构化计划样例测试。

## 系统版本与测试设备（已确认）

- 最低支持系统版本：iOS 16.4。
- 第一版完整真机验收设备：iPhone 16 Pro Max，iOS 26.6。
- 最低版本遵循当前 Expo SDK 的官方支持基线，避免为单一设备增加不必要的构建定制。
- iOS 16.4 及以上属于技术允许安装范围，但第一版不承诺在未经真实测试的旧机型上具有完全相同的通知、动画和性能表现。
- 系统升级后需要重新执行数据库读取、通知安排、通知快捷操作、SecureStore 和动画的核心回归测试。

## 网络请求与错误处理（已确认）

### 超时与取消

- “测试连接”单次最长等待约 15 秒。
- AI 追问和计划生成单次最长等待约 90 秒。
- 请求期间显示明确的生成状态并允许用户取消；取消后保留请求前已经保存的全部输入。
- 第一版使用非流式完整响应，收到完整结果后再统一解析和校验，减少半截 JSON 和中间状态处理风险。

### 重试规则

- 超时、断网或服务器错误后不自动再次调用模型，避免重复请求与意外计费。
- 用户可以手动重新生成、切换另一套模型配置或退出并稍后继续。
- 服务商明确返回可重试等待时间时，将其转成容易理解的提示，但不在后台自动发起请求。
- 格式错误先进行不调用模型的本地清理、JSON 提取和校验；仍失败则保留原始结果作为可恢复草稿，不自动付费请求“修复”。

### 错误分类

- 无网络或域名不可达。
- 请求超时或用户取消。
- API Key 无效或权限不足。
- 模型/接入点不存在。
- 余额不足、配额用尽或请求频率受限。
- 服务商暂时不可用。
- 接口协议或返回格式不兼容。
- 返回内容缺字段、日期错误、任务关系冲突或超过产品限制。

错误日志只记录错误类别、接口配置标识、时间和必要的匿名技术信息，不记录完整 API Key、Authorization 请求头、用户目标正文或完整模型输出。

## 测试与交付方案（已确认）

### 自动化测试

- 自动测试不使用真实 API Key，也不调用收费模型接口。
- 单元测试覆盖数据模型、日期与逾期计算、任务状态转换、任务依赖、计划校验、JSON 解析和错误映射。
- 数据测试覆盖 SQLite 事务、关键操作保存、数据库逐版本迁移、三份恢复副本轮换、损坏副本跳过和恢复流程。
- 通知测试覆盖约 60 条滚动窗口、旧通知取消、改期重排、权限拒绝及任务与通知期望状态核对。
- 模型接口使用本地模拟响应，覆盖成功、取消、超时、断网、认证失败、模型不存在、限流、余额不足、错误 JSON、缺少字段和日期冲突。

### 真实服务商手工验收

- DeepSeek 和豆包分别使用用户自己的 API Key 执行最小连接测试。
- 两者分别完成至少一组“目标追问→计划生成→本地校验→草稿审核”的真实样例。
- 真实调用可能产生由模型服务商收取的少量费用，执行前应由用户确认配置和账号状态。
- 真实 API Key 仅保存在 iPhone SecureStore，不写入项目文件、测试数据、截图、测试报告或版本控制。

### Expo Go 前期验证

- 在 iPhone 16 Pro Max（iOS 26.6）上验证 Expo Go 支持的界面、导航、SQLite、SecureStore 基础用法、本地文件、基础本地通知、网络请求和主要用户流程。
- Expo Go 只作为开发与前期验收容器，不作为最终独立交付形式。
- Expo Go 与以后独立应用的数据容器可能不同，不承诺其中的测试数据自动迁移到独立应用。

### 延期到独立构建的验收项

- 独立的“橙橙计划”名称、图标和启动配置。
- 通知中的“完成”和“延后”快捷操作。
- 应用被系统结束后的通知交互。
- 关机重启、长时间未打开应用和通知滚动补充。
- 独立应用环境中的 SecureStore、数据库恢复和清除全部数据。
- EAS 签名、安装和长期使用方式。

### 当前交付边界

- 当前不注册 Apple Developer Program，不生成独立 iOS 安装包，也不执行 App Store 流程。
- 应用基本完成后，再由用户决定是否开通 Apple Developer Program 并通过 EAS 安装独立版本。
- 在完成延期验收项以前，不得宣称 iOS 独立版本已经完成交付。
